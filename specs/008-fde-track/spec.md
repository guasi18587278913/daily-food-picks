# Feature Specification: 第二条赛道（FDE / AI 工程）

**Feature Branch**: `main`（直接在主线开发）
**Created**: 2026-09-16
**Status**: 需求由用户 2026-09-15 夜间给出；实施进展见 [tasks.md](tasks.md)
**Input**: 用户原话：“我想先做一个，就是 FDE 的版本，你帮我去整理相关的关键词，然后去生成对应的账号内容。但是我希望就是它和现在的美食的监测是两套，就是两个页面，你可以弄一个 tab，然后切换。”
随后明确口径：“我觉得可以直接复用美食博主那一套抓取的流程规则以及一些代码，完全 1:1 的复刻，然后再做出一个 FDE 的来”，理由是“这样我可以测出来它内容质量如何”。

## 背景

产品要从一个博主扩展到多个博主（做 Agent 的、做 FDE 的、做家居的）。第二条赛道的目的不只是多一份内容，而是**用同一把尺子量另一个赛道**：门槛、榜单、预算、判断流程全部不变，只换搜索词和判断主题，这样两边的产出差异才能归因于赛道本身，而不是规则差异。

2026-09-15 夜间的付费探测（13 个关键词、24 次请求，记录在 `.local/fde-probe-20260915/`）给出两条事实：

1. **赛道成立，但“FDE”这个词不成立。** 全部时间维度下 259 条结果里 42 条破千赞、8 条破万，最高 11.7 万。但按首页点赞中位数排，有量的是 AI编程 984、AI Agent 732、AI落地 399、Claude Code 301；而 FDE 84、前向部署工程师 37、解决方案工程师 21。这条赛道实际监测的是“AI 工程落地”，FDE 是其中一个切口。
2. **平台的时间过滤在内容不够时会静默失效。** 用返回结果的真实发布时间核对：`AI编程` + 一天内返回的 20 条全是 0–1 天内的；`AI Agent` + 一天内只有 1 条在一天内，其余 27 到 509 天前。平台不返回空列表，而是退回全站热门。榜单入选按笔记自身发布时间本地判定（`ranking.js` 的 `inWindow`），且候选排序阶段就用搜索结果自带的时间戳把过期的排到最后，所以过期结果进不了榜、也不会浪费详情请求——但它会占掉搜索结果的名额。

用户知悉 1000 赞/24 小时的门槛下 FDE 今日热榜大概率长期为空（真实 24 小时数据最高 101 赞），仍要求保持一致，因为空榜本身就是要测的结论之一。

## User Scenarios & Testing

### User Story 1 - 切换赛道（P1）

成员在首页顶部看到两个标签，点击即可在「深夜食堂」和「AI 工程」之间切换，看到各自的四个榜单。

**Independent Test**: 切换后页面只显示该赛道的轮次与笔记，不混入另一条赛道的内容；切换时清空上一条赛道的缓存与游标。

1. **Given** 页面停在美食赛道，**When** 点击「AI 工程」，**Then** 重新拉取该赛道的最新快照与历史轮次，榜单、状态行、更新时刻全部换成该赛道的。
2. **Given** FDE 赛道尚未发布过任何轮次，**Then** 显示等待首次更新，不借用美食的数据。
3. **Given** 旧版客户端不传赛道，**Then** 按美食赛道返回，行为与加赛道之前一致。

### User Story 2 - 同一套规则下的可比产出（P1）

成员用完全相同的门槛看两条赛道，从而判断 FDE 赛道的内容质量。

**Independent Test**: 两条赛道的轮次形状（一次扫描 + 三轮常规、每轮调用数）逐项相等；四个榜单的门槛取自同一份代码。

1. **Given** 两条赛道都启用，**Then** 每条赛道每天各得一次 100 次调用的扫描和三轮 50 次调用的常规轮，互不挤占。
2. **Given** FDE 赛道当天没有笔记达到今日热榜门槛，**Then** 今日热榜为空，不降低门槛也不用其他榜单填充。

## Requirements

- **FR-101**: 赛道是采集的一等维度。轮次带 `track` 字段；`dfp_snapshots` 记录产出它的赛道；`dfp_state` 的最新指针与状态按赛道分开为 `latest_<track>` / `status_<track>`。`latest` 与 `status` 保留为美食赛道的别名，旧客户端与加赛道前发布的快照继续可读。
- **FR-102**: 两条赛道的采集时刻错开，互不重叠：美食 06:00 扫描 + 09/12/20 常规；FDE 07:00 扫描 + 10/13/21 常规。任一小时至多属于一条赛道，重叠即在 `trackForHour` 抛错，不静默选一条。
- **FR-103**: 赛道之间只有三处不同——搜索词、问模型的问题、决定先花钱查哪条候选的线索。门槛、四个榜单、窗口、预算形状、发布、跨轮去重、快照分片全部共用同一份代码。
- **FR-104**: 判断结果用与赛道无关的词记录：`on_topic` / `off_topic` / `uncertain`。模型仍按各赛道的自然说法作答（美食 `cooking`/`not_cooking`，FDE `practice`/`not_practice`），在 judge 边界翻译。三档内容状态、逐字引用证据、否定必须引用排除词这三条规则对两条赛道完全一致。
- **FR-105**: 每条赛道拿到当天获批额度的等份。`expanded250` 表示**每条赛道** 250 次，整天上限为该数乘以赛道数。配置必须精确等于获批形状（每轨扫描 100、常规 150），多了少了都拒绝加载——只设上限的话，新增赛道会静默把已有赛道的额度减半。
- **FR-106**: 临时补跑轮次预留的额度要覆盖**所有**赛道当天剩余的轮次，不只是自己那条；两条赛道共用一本当日台账，只留自己的会让美食的补跑吃掉 FDE 晚间轮次的额度。
- **FR-107**: 视觉判断只属于美食赛道。画面判定靠“看得见的烹饪动作或带用量的配方”成立，FDE 的录屏没有等价证据。FDE 的视频笔记若步骤只在画面里，停在「未确认」，与美食赛道视觉不可用时的表现一致。
- **FR-108**: catalog 的 `status` 与 `listRounds` 接受 `track` 参数；未知或缺失的值按美食处理，不透传到存储。加赛道前发布的快照没有 `track` 字段，按美食计入。

## Success Criteria

- **SC-101**: 两条赛道的日程形状逐项相等（各一次 100 次扫描、三轮 50 次常规），且没有任何小时同时属于两条赛道。
- **SC-102**: 同一条笔记在两条赛道下由各自的提问得到各自的判断；一条赛道的判定词喂给另一条赛道会被拒为 `uncertain`。
- **SC-103**: 把整天额度配成加赛道之前的数值（250/100）会被拒绝加载，而不是把每条赛道压到一半。
- **SC-104**: 客户端切换赛道后不残留上一条赛道的笔记、轮次或游标；不传赛道的调用仍返回美食赛道。
- **SC-105**: 全量测试、类型检查、包检查通过；部署后线上代码与源码一致。

## Assumptions

- FDE 赛道的今日热榜在 1000 赞门槛下长期为空是预期结果，不是故障。用户要的是在同一把尺子下的对比结论。
- 关键词随时可改：`config/keywords/<track>.json` 是该赛道的全部词表，改词不需要动代码。
- 两条赛道共用一本当日预算台账与一把采集锁，因此轮次必须错开小时；这是当前设计能支持的赛道数上限的来源。

# Feature Specification: 微信登录与多用户权限体系

**Feature ID**: `003-wechat-login-roles`

**Feature Branch**: 待定；功能目录与 Git 分支名独立。

**Created**: 2026-09-13

**Status**: 本地实现与验证已完成（`npm test` 154 通过）；云端部署、配额回读、白名单迁移和真机验收待完成。进度以[任务清单](tasks.md)为准，部署与验收事实见[运行记录](../../docs/operations/multi-user-access-runbook.md)。本文件维护需求和验收约定。

**Input**: 用户要求把产品从单人试用扩展到 10–100 个用户，用微信登录，并做好相关权限。已确认决策：邀请码自助开通；权限两档 admin 与 member；新增仅管理员可见的小程序内管理页；收藏改为云端按用户存储并迁移本地已有收藏。身份仍来自微信平台本次调用上下文，不新增手机号、头像、昵称采集。个人主体不支持微信支付，本次不做付费。

## 与既有需求的关系

本功能修订 [001 功能规格](../001-wechat-member-trial/spec.md) 的 FR-023：该条原定"按单个实际使用者设计，不建设自助注册、多客户管理"。用户已明确产品要服务 10–100 个用户，因此自助开通与用户管理进入范围。**付费订阅仍不在范围内**，原因是个人主体不具备微信支付开通资质，而非需求不存在。

001 的以下约定继续有效，本功能不得削弱：

- FR-017：供应商密钥、云凭据、原始采集记录只在服务端使用，不打包或返回给客户端。
- FR-018：云端读取必须核验平台可信身份；不能相信客户端自报的成员身份。数据库和私有图片不允许客户端任意读写或签发链接。
- FR-019：试用者不需要提供手机号、头像、昵称或小红书登录凭据。
- FR-009：页面只读已保存结果，打开、刷新、搜索或收藏均不得触发收费采集。

001 的 T032（指定成员真机验收）独立于本功能，不因本功能改动而视为完成或作废。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新用户凭邀请码自助开通 (Priority: P1)

拿到邀请码的人扫码进入小程序，看到开通引导，输入邀请码后立即可用，不需要联系维护者、不需要等人审批、不需要提供手机号或任何个人资料。

**Why this priority**: 这是从单人白名单走向多用户的唯一入口。没有它，每增加一个用户都要维护者改配置并重新部署云函数。

**Independent Test**: 用一个从未开通过的真实微信账号扫码进入，确认只看到开通引导而没有任何选题数据；输入有效邀请码后能看到完整选题内容；用同一个码让第二个账号开通，直到达到该码的次数上限后被拒绝。

**Acceptance Scenarios**:

1. **Given** 某微信账号从未开通，**When** 进入小程序，**Then** 显示开通引导和邀请码输入入口；不返回任何选题作品、图片地址、轮次信息或采集日志。
2. **Given** 持有有效且未用尽的邀请码，**When** 提交该码，**Then** 立即开通为 member，当前会话无需重启即可看到选题内容，并记录开通时间和所用邀请码。
3. **Given** 提交的码不存在、已停用、已过期或已达次数上限，**When** 校验，**Then** 分别给出可区分的失败提示，不开通，不泄露该码是否曾经存在。
4. **Given** 同一个账号重复提交同一个有效码，**When** 校验，**Then** 不重复扣减该码剩余次数，不产生第二条用户记录。
5. **Given** 两个账号在同一时刻提交同一个仅剩一次的码，**When** 并发处理，**Then** 只有一个成功开通，另一个收到已用尽提示；剩余次数不会变成负数。
6. **Given** 已开通的 member 再次进入，**When** 打开页面，**Then** 直接进入选题内容，不再出现邀请码输入。
7. **Given** 账号连续多次提交错误邀请码，**When** 达到设定的尝试上限，**Then** 暂时拒绝继续尝试并说明恢复时间，不因此封禁已开通用户。

---

### User Story 2 - 管理员在小程序里管理用户和邀请码 (Priority: P1)

维护者用自己的微信打开小程序，进入只有管理员可见的管理页，查看已开通用户、停用滥用账号、生成新的邀请码发给客户，不需要开电脑、不需要登录云控制台、不需要手敲数据库字段。

**Why this priority**: 没有管理入口，邀请码无处产生，用户状态无法调整，User Story 1 无法运转。两者必须同时交付。

**Independent Test**: 用管理员账号进入，确认能看到管理入口并完成生成码、查看用户列表、停用和恢复；用 member 账号确认完全看不到管理入口，且直接调用管理接口会被拒绝。

**Acceptance Scenarios**:

1. **Given** 当前账号是 admin，**When** 打开小程序，**Then** 能看到管理入口；member 和未开通账号看不到该入口。
2. **Given** member 或未开通账号绕过界面直接请求管理能力，**When** 服务端处理，**Then** 一律拒绝，不返回用户列表、邀请码明文或其他用户的任何信息。
3. **Given** admin 在管理页生成邀请码，**When** 指定次数上限和有效期，**Then** 得到可复制的码，并记录创建者和创建时间。
4. **Given** admin 查看用户列表，**When** 列表超过一页，**Then** 能继续翻页；显示每个用户的状态、角色、开通时间和所用邀请码，不显示手机号、昵称、头像等未采集的资料。
5. **Given** admin 停用某个 member，**When** 该用户下次请求，**Then** 拒绝其读取选题数据并说明已停用；其收藏数据保留不删除。
6. **Given** admin 恢复被停用的用户，**When** 该用户重新进入，**Then** 恢复正常读取，原有收藏仍在。
7. **Given** admin 停用某个邀请码，**When** 有人提交该码，**Then** 开通失败；已用该码开通的用户不受影响。
8. **Given** admin 尝试停用自己或移除自己的管理角色，**When** 提交，**Then** 拒绝该操作，保证系统始终至少有一个可用的 admin。

### User Story 3 - 收藏跟人走，换设备不丢 (Priority: P2)

用户在手机上收藏的选题，换手机、重装小程序后依然在；每个人的收藏只属于本人，看不到也不影响别人的收藏。

**Why this priority**: 多用户场景下收藏必须与身份绑定。本机存储在换设备时静默丢失，且无法保证多用户隔离。现有单人用户的本地收藏不能在升级时丢掉。

**Independent Test**: A 账号收藏若干作品，清除小程序存储后重新进入，确认收藏仍在；B 账号进入确认看不到 A 的收藏；用一个本地已有收藏的账号升级后进入，确认原收藏被保留。

**Acceptance Scenarios**:

1. **Given** 用户收藏或取消收藏，**When** 保存成功，**Then** 状态同步；换设备或重装后用同一微信账号进入，收藏仍在。
2. **Given** 保存失败，**When** 收藏，**Then** 明确提示失败，不显示虚假成功状态，不丢弃已有收藏。
3. **Given** 升级前本机已有收藏，**When** 首次进入新版本，**Then** 本地收藏合并进云端；重复条目只保留一份，合并失败时保留本地副本并提示，不静默丢失。
4. **Given** 云端已有收藏而本机也有不同记录，**When** 合并，**Then** 取两者并集，不用空的一侧覆盖另一侧。
5. **Given** 用户被停用，**When** 请求收藏，**Then** 拒绝读取；恢复后收藏完整可见。
6. **Given** 已收藏作品已不在最新轮次，**When** 查看收藏，**Then** 仍能从往期找到；目标不可用时提示并允许取消。
7. **Given** 任何用户，**When** 请求收藏数据，**Then** 只能读写自己的收藏，无法通过参数读取或修改他人收藏。

---

### User Story 4 - 从单人白名单平滑切换 (Priority: P1)

切换到新机制时，现有已授权的账号不掉线、不需要重新要码；维护者在切换后仍能管理系统。

**Why this priority**: 001 的指定成员验收仍在进行中。切换过程让现有用户失去访问，等于中断已交付的试用。

**Independent Test**: 在现有白名单有记录的状态下完成迁移，用白名单中的账号进入，确认无需邀请码即可使用；确认至少一个账号具备 admin 能力；确认迁移重复执行不产生重复或冲突记录。

**Acceptance Scenarios**:

1. **Given** 现有环境变量白名单中的账号，**When** 迁移完成后进入，**Then** 直接以已开通身份使用，不要求输入邀请码。
2. **Given** 迁移脚本或流程被重复执行，**When** 再次运行，**Then** 不产生重复用户记录，不覆盖已变更的角色或状态。
3. **Given** 系统中还没有任何 admin，**When** 引导初始管理员，**Then** 依据服务端配置而非客户端请求确定该身份，并在管理页可见。
4. **Given** 迁移后白名单环境变量被清空，**When** 已迁移用户进入，**Then** 仍可正常使用；权限判定来源唯一，不出现新旧两套判定同时生效。

### Edge Cases

- 邀请码被猜测或批量尝试；同一码被同时提交；码的剩余次数与实际开通数不一致。
- 码已过期但用户界面仍显示可用；码在提交过程中被管理员停用。
- 用户开通瞬间被停用；停用与恢复同时发生；角色在一次会话中途变化。
- 最后一个 admin 被停用或降级；admin 自己的用户记录被误删。
- 用户数量增长导致前台轮询、云函数调用和数据库读取超出免费额度。
- 收藏合并时本地数据损坏、条目超量、云端写入部分成功。
- 同一人换设备后旧设备仍在轮询；同一账号多设备同时收藏同一作品。
- 未开通用户通过构造请求直接访问选题、图片链接、用户列表或他人收藏。
- 迁移中途失败；新旧权限判定并存期间的行为；环境变量与数据库记录冲突。

## Requirements *(mandatory)*

### Functional Requirements

#### 身份与权限判定

- **FR-001**: 用户身份必须来自微信平台在本次云端调用中提供的 AppID 与 OpenID，不得采纳客户端请求参数中自报的身份，不得沿用上一次调用遗留的进程状态。
- **FR-002**: 权限判定的唯一依据是服务端用户记录中的角色与状态。迁移完成后，服务端配置里的静态身份名单不再作为业务授权来源。
- **FR-003**: 角色只有 admin 和 member 两档。member 可读取选题数据和自己的收藏；admin 额外具备用户与邀请码管理能力。
- **FR-004**: 用户状态至少区分已开通、已停用两种。未开通的账号在系统中可以没有记录，其表现与无权限一致。
- **FR-005**: 未开通和已停用账号不得获得任何选题作品、图片地址、轮次元数据、采集日志、用户列表或他人收藏；拒绝原因对用户可读，但不透露系统内部细节。
- **FR-006**: 每个需要权限的服务端入口独立校验身份与权限，不依赖调用方声明已校验过，也不依赖界面是否隐藏入口。
- **FR-007**: 不采集手机号、头像、昵称、地理位置或小红书凭据。开通流程只需要邀请码。

#### 邀请码

- **FR-008**: 邀请码由 admin 生成，必须支持次数上限和有效期。码的生成只在服务端进行，不由客户端构造。
- **FR-009**: 邀请码必须具备足以抵抗猜测的随机性，并排除易混淆字符；提交时不区分大小写和首尾空白。
- **FR-010**: 邀请码核销必须是原子操作：并发提交同一个仅剩一次的码时只能有一个成功，剩余次数不得为负，不得出现超额开通。
- **FR-011**: 同一账号重复提交同一个已为其开通的码，不重复扣减次数、不重复创建用户记录，并提示已开通。
- **FR-012**: 码不存在、已停用、已过期、已用尽分别给出可区分提示，且不泄露码是否曾经存在。
- **FR-013**: 必须限制单个账号的错误提交频率，达到上限后暂时拒绝并说明恢复条件；该限制不影响已开通用户的正常读取。
- **FR-014**: admin 可停用邀请码。停用只影响后续开通，不回收已经用该码开通的用户。
- **FR-015**: 记录每个用户开通时所用的邀请码、开通时间，以及每个码的创建者、创建时间、已用次数。

#### 管理能力

- **FR-016**: 提供仅 admin 可见的管理入口，支持查看用户列表（分页）、停用与恢复用户、生成与停用邀请码。
- **FR-017**: 管理页显示的用户信息限于系统自身记录：身份编号、角色、状态、开通时间、所用邀请码。不显示未采集的个人资料。
- **FR-018**: 系统必须始终保留至少一个可用的 admin。拒绝会导致无可用 admin 的停用或降级操作，包括 admin 对自己的操作。
- **FR-019**: 初始管理员由服务端配置引导确定，不能通过邀请码或客户端请求自行取得 admin。
- **FR-020**: 所有改变权限状态的操作（开通、停用、恢复、角色变更、生成与停用邀请码）记录操作者、时间和对象，可供事后核对。

#### 收藏

- **FR-021**: 收藏按用户身份保存在服务端，换设备或重装后用同一微信账号可见。
- **FR-022**: 任何用户只能读写自己的收藏；不得通过请求参数读取或修改他人收藏。
- **FR-023**: 首次进入新版本时把本机已有收藏合并进服务端，取并集去重；合并失败保留本地副本并提示，不静默丢失收藏。
- **FR-024**: 收藏写入失败必须明确提示，不显示虚假成功，不清空已有数据。
- **FR-025**: 停用用户的收藏数据保留不删除，恢复后完整可见。

#### 迁移与容量

- **FR-026**: 迁移必须可重复执行且结果一致：把现有白名单账号建成已开通用户记录，不产生重复记录，不覆盖已变更的角色或状态。
- **FR-027**: 迁移完成前后，权限判定来源必须唯一明确，不允许新旧两套判定同时生效导致行为不确定。
- **FR-028**: 必须先核实 10–100 用户规模下前台轮询、云函数调用、数据库读写和存储的实际用量与免费额度关系，明确是否需要调整轮询策略或申请额度，并记录依据。缺少该核实不得按 100 用户规模对外开通。
- **FR-029**: 新增能力不得触发收费采集。开通、登录、管理操作和收藏读写均只访问已保存数据。
- **FR-030**: 本次不建设付费订阅、支付、发票或订单能力。个人主体资质限制须在功能文档中如实记录，不承诺未取得的能力。

### Key Entities *(include if feature involves data)*

- **用户（User）**: 代表一个微信账号在本产品中的访问资格。关键属性：身份编号、角色（admin / member）、状态（已开通 / 已停用）、开通时间、所用邀请码、最近一次变更记录。不含手机号、昵称、头像。
- **邀请码（InviteCode）**: 代表一次可分发的开通凭据。关键属性：码值、次数上限、已用次数、有效期、是否停用、创建者、创建时间。与用户是一对多关系。
- **用户收藏（UserFavorites）**: 代表某个用户收藏的作品集合。关键属性：所属用户、作品编号列表及各自收藏时间。只能由所属用户读写。
- **权限变更记录（AccessAuditEntry）**: 代表一次权限相关操作。关键属性：操作者、操作类型、对象、时间、结果。用于事后核对，不用于业务判定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从扫码到看到选题内容，只需输入一次邀请码，整个过程不超过 1 分钟，且不需要提供任何个人资料。
- **SC-002**: 维护者新增一个用户不再需要修改配置或重新部署服务端；生成一个可分发的邀请码在管理页 30 秒内完成。
- **SC-003**: 未开通、已停用账号在全部数据入口上的访问尝试 100% 被拒绝，且拒绝响应中不含任何选题作品、图片地址或其他用户信息。
- **SC-004**: 并发核销同一个仅剩一次的邀请码，超额开通发生率为 0。
- **SC-005**: 换设备或清除本地存储后，用同一微信账号重新进入，收藏找回率 100%。
- **SC-006**: 升级迁移后，原有已授权账号 100% 无需重新开通即可继续使用；系统始终存在至少一个可用管理员。
- **SC-007**: 在已核实的用量结论范围内支撑目标用户规模，不因用户增长产生未预期费用。

## Assumptions

以下是在用户未明确说明处采用的合理默认。审阅时如与预期不符，请指出后更新本规格。

- **开通方式唯一**：只有邀请码一条自助路径，本次不做"申请后审批"流程。用户已在决策中选择邀请码方案。
- **被停用用户不能自助恢复**：停用后即使持有有效邀请码也不能重新开通，必须由 admin 恢复。这样停用才有实际约束力。
- **邀请码可多次使用**：次数上限由生成时指定，不限定为一次性。用户明确要求"可限次数"。
- **初始管理员沿用服务端配置引导**：保留一个服务端配置项指定初始 admin 身份，仅用于引导，不作为业务授权来源。
- **角色不支持自助申请**：member 无法申请升级为 admin，只能由现有 admin 指派。
- **用户记录不支持自助注销**：本次不做用户自行删除账号与数据；如有需要另立功能。
- **收藏以服务端为准**：合并完成后服务端是权威来源，本机存储只作为离线兼容与迁移来源。
- **目标规模 100 用户**：容量、费用和轮询策略按此上限核实，不按更大规模设计。
- **沿用现有技术栈**：原生微信小程序与现有云函数、数据库，不引入新的身份服务或第三方登录。
- **不改变选题业务规则**：采集窗口、入选门槛、倍数计算、去重规则均不在本次范围，保持 001 已确认的行为。
- **付费能力受主体资质限制**：个人主体不能开通微信支付。若将来要收费，需先变更主体资质，属于独立决策。

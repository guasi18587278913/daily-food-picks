# 发布与版本记录

目的：让 GitHub 上随时能查到"线上跑的是哪份代码"。每个正式发布的版本在仓库里对应一个 tag 和一条 Release 记录。

## 为什么是这个方向

GitHub 是版本的来源，不是线上的副本。

先提交、再打 tag、再从这份代码上传微信，一致性是天然成立的。反过来做（先上传、事后同步）无法证明同步的就是上传的那份：本地任何未提交改动都会让两边悄悄分叉。

微信没有开放自动提审和自动发布的接口（第三方平台 API 需要服务商资质）。所以提交审核和点击发布始终是人工步骤，这里不做自动化。

## 发布一个版本

1. 确认要发布的代码已合并进 `main` 并推送。
2. 在微信开发者工具上传代码，版本号与下面要打的 tag 保持一致。
3. 微信后台提交审核，等待通过。
4. 审核通过、点击"发布"之后，回到仓库根目录执行：

```bash
npm run release -- 1.0.0 --note="本次改动一句话"
```

发布日期默认取当天。补记历史版本时用 `--date=2026-09-13` 指定微信后台实际发布的日期。

## 这条命令做了什么

| 阶段 | 内容 | 不通过时 |
| --- | --- | --- |
| 状态检查 | 工作区干净、当前在 `main`、与 `origin/main` 一致、tag 未被占用 | 直接停止，不产生任何改动 |
| 交付检查 | `npm test`、`npm run typecheck:mini`、`npm run check:package` | 打印失败输出并停止 |
| 写入版本 | `package.json` 版本号改为目标值并提交；已是目标值时不新增提交 | — |
| 打 tag | 附注 tag，记录微信后台版本号、发布日期和说明 | — |
| 推送 | 推 `main` 和 tag | 提示用 `git tag -d` 撤销本地 tag |
| Release | 用 `gh` 创建 GitHub Release，附自动生成的变更日志 | tag 已推送成功，提示手动补建命令 |

命令本身不上传代码、不部署云函数、不碰微信后台。它只负责把"这个版本已经上线"这件事记进仓库。

## 查历史版本

```bash
git tag -l                 # 所有发布过的版本
git tag -n99 v1.0.0        # 某个版本的发布日期和说明
git checkout v1.0.0        # 切到该版本的代码
git diff v1.0.0..main      # 线上版本与当前 main 的差异
```

Releases 页面：https://github.com/guasi18587278913/daily-food-picks/releases

## 版本号怎么定

与微信后台填写的版本号一一对应，三段式 `x.y.z`。同一个版本号只能发布一次。

云函数单独部署、小程序代码未变时，不需要新版本号；有实际线上行为变化才记一次发布。

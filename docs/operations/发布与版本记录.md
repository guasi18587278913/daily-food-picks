# 发布与版本记录

目的：让 GitHub 上随时能查到"线上跑的是哪份代码"。每个正式发布的版本在仓库里对应一个 tag 和一条 Release 记录。

## 两件不同的事

| 目标 | 靠什么保证 | 是否自动 |
| --- | --- | --- |
| GitHub 上一定有线上那份代码，不会落后 | 提交后自动推送 | 全自动 |
| 一眼看出哪一份是线上正式版 | tag 和 GitHub Release | 你说一句，其余自动 |

`main` 分支通常会**领先**线上——发布之后你还在继续开发，这是正常的。所以"两边完全相等"不是目标，目标是上面这两条。

## GitHub 不落后于本地

每次提交后，当前分支会自动推到 GitHub。推送在后台进行，不拖慢提交，失败也不会让提交回滚。

这由 git 的 `post-commit` 钩子实现，安装在 `.git/hooks/post-commit`。git 钩子不随仓库分发，所以**换机器或重新克隆之后要再装一次**：

```bash
npm install          # 会自动安装
# 或者
node scripts/install-hooks.js
```

推送记录写在 `.local/auto-push.log`（不进仓库）。没网或远程有新提交时推送会失败，这时会话开始的检查会提示你还有几个提交没上去。

想临时关掉：删除 `.git/hooks/post-commit` 即可，其它功能不受影响。

## 会话开始时的检查

每次在这个项目里打开 Claude Code，会自动跑一次 `scripts/check-sync.js`：

- 有提交没推上 GitHub → 提示（说明自动推送失败过）
- 距上次发布记录超过 14 天且期间有新提交 → 提醒补记，同一提醒 7 天内不重复

一切正常时它不说话。手动查状态用 `npm run check:sync`。

## 为什么是这个方向

GitHub 是版本的来源，不是线上的副本。

先提交、再打 tag、再从这份代码上传微信，一致性是天然成立的。反过来做（先上传、事后同步）无法证明同步的就是上传的那份：本地任何未提交改动都会让两边悄悄分叉。

微信没有开放自动提审和自动发布的接口（第三方平台 API 需要服务商资质）。所以提交审核和点击发布始终是人工步骤，这里不做自动化。

## 发布一个版本

1. 确认要发布的代码已合并进 `main` 并推送。
2. 在微信开发者工具上传代码，版本号与下面要打的 tag 保持一致。
3. 微信后台提交审核，等待通过。
4. 审核通过、点击"发布"之后，回到仓库根目录执行：

```bash
npm run release -- 1.0.0 --note="本次改动一句话"
```

发布日期默认取当天。

隔了几天才想起来记录时，用补记模式指定当时上线的那份代码：

```bash
npm run release -- 1.0.0 --commit=<那次上传对应的提交> --date=2026-09-16
```

补记模式只校验该提交确实在 `origin/main` 上，不跑当前工作区的交付检查、不改 `package.json`——那份代码早已上线，检查现在的工作区证明不了它。

不确定是哪个提交时，直接告诉 Claude 版本号和大概日期，由它查出来。

## 这条命令做了什么

以下是当天发布模式（不带 `--commit`）。补记模式只做 tag 未被占用和提交在 `origin/main` 上这两项校验，然后直接打 tag、推送、建 Release。

| 阶段 | 内容 | 不通过时 |
| --- | --- | --- |
| 状态检查 | 已跟踪文件没有未提交改动、当前在 `main`、与 `origin/main` 一致、tag 未被占用 | 直接停止，不产生任何改动 |
| 交付检查 | `npm test`、`npm run typecheck:mini`、`npm run check:package` | 打印失败输出并停止 |
| 写入版本 | `package.json` 版本号改为目标值并提交；已是目标值时不新增提交 | — |
| 打 tag | 附注 tag，记录微信后台版本号、发布日期和说明 | — |
| 推送 | 推 `main` 和 tag | 提示用 `git tag -d` 撤销本地 tag |
| Release | 用 `gh` 创建 GitHub Release，附自动生成的变更日志 | tag 已推送成功，提示手动补建命令 |

命令本身不上传代码、不部署云函数、不碰微信后台。它只负责把"这个版本已经上线"这件事记进仓库。

## 查历史版本

```bash
git tag -l                 # 所有发布过的版本
git tag -n99 v1.0.0        # 某个版本的发布日期和说明
git checkout v1.0.0        # 切到该版本的代码
git diff v1.0.0..main      # 线上版本与当前 main 的差异
```

Releases 页面：https://github.com/guasi18587278913/daily-food-picks/releases

## 版本号怎么定

与微信后台填写的版本号一一对应，三段式 `x.y.z`。同一个版本号只能发布一次。

云函数单独部署、小程序代码未变时，不需要新版本号；有实际线上行为变化才记一次发布。

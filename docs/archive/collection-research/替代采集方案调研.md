# 替代采集方案调研

查验日期：2026-09-08。当前组合试跑已按用户要求停止；本次调研没有新增付费调用，也没有安装或运行新的小红书采集工具。

## 结论

有新的开源读取方式可以验证，但没有找到已经证实能同时满足“广泛发现候选、每轮实时读取作者此前10条、稳定运行、低费用”的现成替代。

下一步应先减少不必要的作者查询，再验证精简的直接接口读取层。仅换一个MCP或浏览器，不会让几千个作者的读取工作消失。账号访问限制也没有被新工具证明解决。

值得保留的工程方向有两个：

1. 以本地接口客户端承担搜索、详情、作者列表，浏览器只处理必要的登录。xhshow可作为签名模块，其他客户端提供分页和错误处理参考，但不能直接视为已经可用的完整系统。
2. 用持续保留登录状态、隔离任务页签的浏览器作小范围对照。Ego Lite是本次X讨论中新找到的候选，但它是浏览器替代，不是新增的小红书数据源。

## 1. 这轮试跑真正暴露了什么

- 浏览器取得4,214篇不同候选，API交叉搜索取得159篇，两边合并去重后为4,322篇。
- 合并候选涉及4,041位不同作者。假设每位作者一次TikHub列表查询就足够，作者参照部分也约为40.41美元；详情、搜索和额外翻页另计。这是成本结构估算，不是实际支出。[TikHub单价](https://tikhub.io/xiaohongshu-api)
- 浏览器尝试读取384位作者，其中304位取得非空作品数据；后来搜索页和作者页出现登录提示。尚未确定是过期、访问频率还是其他会话问题，不能声称已经查明封号原因。
- 本轮API实际调用162次：158次有效业务响应、4次HTTP 403。按所有尝试均计费的保守口径为1.62美元；按成功次数与公开单价为1.58美元，未核对账单。早先6次小样本验证另计。
- 7篇仅达到数值条件，暂停时只完成其中3篇的制作内容与详情时间核对。不能把7篇全部称为已推荐爆款，也不能把未处理的候选当作不达标。

一次页面读取很快，不代表连续读取几百个作者仍稳定。一个接口调用成功，也不代表整轮费用适合个人工作台。这是本次选型需要修正的判断。

具体阶段记录见[组合试跑阶段记录](./采集验证/2026-09-08组合试跑/阶段记录.md)。

## 2. 新开源项目对照

CLI是可以由程序调用的命令行工具。它可以直接请求接口，也可以在背后启动浏览器；名称相似不代表取数方式相同。

| 项目 | 实质能力 | 对本工作台的判断 |
| --- | --- | --- |
| Cloxl/xhshow | 本地生成小红书请求签名，纯Python，MIT | 可作精简接口层的基础；不是完整采集器，没有作者前10条与覆盖验收逻辑 |
| tamnd/xiaohongshu-cli | Go单文件，详情优先读网页内嵌数据，区分多类拒绝状态，完整Apache-2.0许可 | 可借鉴读取与错误处理；搜索筛选、作者时间/置顶、精确点赞和恢复流程仍有缺口 |
| jackwener/xiaohongshu-cli | Python直接接口客户端，搜索排序/类型/页码、作者游标，依赖xhshow | 比从零组织接口完整，但缺时间筛选；主分支较旧，不升为当前首选 |
| jackwener/xhs-cli | Camoufox浏览器版，读取页面状态 | 与上一行是不同项目；仍属于浏览器路线，不能宣传为免浏览器取数 |
| lucasygu/redbook | TypeScript直接接口、作者游标、多作者报表，MIT | 缺时间筛选，时间处理存在编辑时间兜底；批量报表仍逐个查询作者 |
| cv-cat/Spider_XHS | 新版搜索接口、本地签名、搜索及作者分页，9月7日刚更新算法 | 接口参考较新；README禁止商业化，不能直接当作已获许可的业务底座 |
| JoeanAmier/XHS-Downloader | 读取已知笔记的详情字段，可关闭媒体下载 | 适合补详情；作者分页模块未完成，搜索发现仍靠浏览器脚本 |
| ReaJason/xhs / MediaCrawlerPro | 登录、签名、HTTP读取分离的架构先例 | 前者维护较旧；后者核心源码访问受限且有商业限制，不直接选作现成方案 |

### xhshow：是签名模块，不是稳定性保证

签名是平台检查请求时使用的校验信息。xhshow在本地生成这类信息，支持作者列表等请求。项目有MIT许可证，最新发布为2026年6月11日v0.2.0。作者把会话管理的长期效果标为待验证。[项目说明](https://github.com/Cloxl/xhshow)、[发布记录](https://github.com/Cloxl/xhshow/releases/tag/v0.2.0)

使用它可以减少对页面加载的依赖，仍需要处理账号登录、分页、数据字段和平台拒绝。没有证据支持“换成它就不掉登录”。

### tamnd：错误处理值得参考，完整采集仍不合格

主分支8月19日增加了错误分类，最新版Release仍停留在6月13日。搜索目前固定综合排序和类型不限，没有时间筛选；作者列表没有时间和置顶字段，仍须补详情。[维护提交](https://github.com/tamnd/xiaohongshu-cli/commit/b60f9a384ed32d002aaacbbff95fedb2bdc96682)、[搜索源码](https://github.com/tamnd/xiaohongshu-cli/blob/b60f9a384ed32d002aaacbbff95fedb2bdc96682/xiaohongshu/search.go#L68-L124)、[作者实现](https://github.com/tamnd/xiaohongshu-cli/blob/b60f9a384ed32d002aaacbbff95fedb2bdc96682/xiaohongshu/user.go#L182-L277)

详情区分发布时间和更新时间，但会把“1.9万”转成19000，丢失原始精度含义。用于严格倍数判断时，需要保留约数标记或补查精确数。[约数处理](https://github.com/tamnd/xiaohongshu-cli/blob/b60f9a384ed32d002aaacbbff95fedb2bdc96682/xiaohongshu/ssr.go#L167-L191)

不能把边运行边保存说成断点续跑：当前crawl的队列只在内存，再次运行会重开输出文件，失败项还可能被跳过后整体返回成功。默认响应缓存也需要处理，不能把旧赞数作为下一轮新数据。[文件与队列](https://github.com/tamnd/xiaohongshu-cli/blob/b60f9a384ed32d002aaacbbff95fedb2bdc96682/cli/meta.go#L238-L355)、[默认缓存](https://github.com/tamnd/xiaohongshu-cli/blob/b60f9a384ed32d002aaacbbff95fedb2bdc96682/cli/root.go#L69-L81)

### 两个jackwener项目不能混用结论

`xiaohongshu-cli`是直接接口版，`xhs-cli`是浏览器版。直接接口版主分支最后提交为2026年3月21日；搜索请求时间条件固定不限，作者数据直接透传，尚需验证字段。README和包元数据声明Apache-2.0，但树中缺独立LICENSE文件，正式采用前仍需澄清。[直接接口版](https://github.com/jackwener/xiaohongshu-cli)、[固定筛选条件](https://github.com/jackwener/xiaohongshu-cli/blob/4d63f3c0c85ccd9054fa8e96d7f761aaf2507449/xhs_cli/client_mixins.py#L29-L39)、[浏览器版](https://github.com/jackwener/xhs-cli)

### 最新签名并不等于账号问题已经解决

Spider_XHS在9月7日更新PC签名算法，当前搜索走v2入口。它有时间筛选的兼容参数，但本次没有实测其效果；README明确禁止商业化。[更新](https://github.com/cv-cat/Spider_XHS/pull/184)、[搜索实现](https://github.com/cv-cat/Spider_XHS/blob/7077c88f82771f547cc1afdadaec4025be2355e6/apis/xhs_pc_apis.py#L928-L1035)、[使用限制](https://github.com/cv-cat/Spider_XHS/blob/7077c88f82771f547cc1afdadaec4025be2355e6/README.md#L56-L73)

redbook有用户报告同一机器上“能读详情、不能搜索”的账号差异。这是提交者的对照经验，尚非平台官方解释，也不能直接作为我们登录失效的定因。[原始问题单](https://github.com/lucasygu/redbook/issues/13)

## 3. X上的经验，哪些能支持选型

本次分5组关键词检索X，读取重点帖子和可见讨论；没有声称读完全部评论。搜索中的长文、引用和关键词误命中较多，已排除与采集无关的内容。

- **Ego Lite：可作为浏览器对照。** 8月15日用户推荐其小红书自动化体验；可见回复有正面反馈，也提醒不能轻信“不易识别”。官网确认Mac版免费、共享已有登录状态和隔离任务工作区。没有取得连续处理几千位小红书作者的成功率数据。[X原帖与讨论](https://x.com/LinearUncle/status/2088603102425628696)、[官网](https://lite.ego.app/zh-cn)
- **CLI作者介绍：证明项目确实做了接口接入，未证明批量稳定。** 作者3月介绍了搜索、阅读及请求处理；回复里也有人询问账号限制。没有看到可用来保证本工作台规模的运行记录。[作者原帖](https://x.com/jakevin7/status/2031412457537704358)
- **TikHub使用者好评：工作量口径不同。** 8月19日用户及回复认可省维护和价格，但没有给每轮几千位作者、每人十条参照的成本。不能把“我觉得便宜”直接套到本项目。[原帖与回复](https://x.com/bozhou_ai/status/2089954572081185097)
- **只读操作也有受限的个案反馈。** 9月4日一位用户自述仅做浏览也遇到账号限制。缺少请求规模、配置与服务端证据，不能据此推导封号率。[原回复](https://x.com/LBan2049/status/2095758546713690337)
- **很多展示是小量选题研究。** 一条CLI体验搜索摘要举例按热度取10篇研究正文和评论；本次该帖全文读取未成功，因此仅把它作为检索线索。[原帖](https://x.com/Bearlagcy/status/2054842492143718572)

Ego Lite不是已经核实为开源的完整采集器。它能改善浏览器协作和登录使用体验，不会自动扩大平台数据覆盖，也不会取消几千次作者读取。

## 4. 现成数据服务未证实更划算

核对公开费用时，要把候选和历史参照一起算。假设1000篇候选对应1000位不同作者，至少涉及1000篇候选和10000条参照。

Apify上Habit的服务公开列表费用为5美元/1000条。按上述理想记录量计算约55美元，若作者列表再次返回候选本身则约60美元，额外详情和冗余记录另计。它可以省维护，但这个公开方案不是更便宜的替代。[服务说明与价格](https://apify.com/habit.zhou/xiaohongshu-pro-scraper)

千瓜当前公开套餐包含作者详情查看、导出、更新等不同额度，不能把包月当作无限取数。新榜有定制API入口说明，但没有核实本任务的完整报价、收录延迟与刷新保证；灰豚同样缺少必要的公开细节。[千瓜价格](https://www.qian-gua.com/Home/AllPrice?typeId=1)、[高档权益](https://www.qian-gua.com/Home/AllPrice?typeId=2)、[新榜](https://www.newrank.cn/)、[灰豚](https://xhs.huitun.com/)

小红书官方账号开放平台当前公开的是授权后基本资料，分享平台负责分享发布。没有找到可直接申请的全站关键词搜索和任意作者历史入口。[官方接口目录](https://openaccount.xiaohongshu.com/docs/api-reference)、[分享开放平台](https://agora.xiaohongshu.com/)

## 5. 优先尝试不缩小候选覆盖的优化

### 用既有五倍规则提前停止不必要的查询

在点赞数为精确非负整数、参照取10条的条件下，只要中位数大于0，它最小就是0.5。达到5倍至少需要2.5赞，所以精确的0、1、2赞都不可能达标；中位数为0或不足10条本来就不判定为五倍爆款。

这轮4,322篇候选中，2,191篇的已取得搜索点赞为精确0–2赞。如果固定使用该次读到的赞数作为本轮判断值，所需作者可从4,041位降到1,995位，理论上少查询2,046位作者，约50.6%。

这是离线估算，尚未实施。它不删除候选，不设推荐条数配额；后续轮次仍重新取数，点赞上涨后可以继续参与。若准备在同轮稍后刷新候选赞数，则需基于刷新后的数值重新判断，不能仍沿用先前的0–2赞结论。约数、下界和缺失值都不使用这项提前判定。

即使这样优化，剩余作者若全部用每次0.01美元的API，理想一页成本仍约19.95美元。它显著减少请求，但不能单独把整轮压到5美元。

### 把明确不相关的内容挡在作者查询前

这轮数值达标候选里已经出现宠物比喻、互动图片或鞋类营销的标题线索，不能因为搜索词是“烘焙”“创意料理”就视为制作教程。应优先利用已取得的标题、摘要和封面判断明确不相关内容；模糊的保留待核对，不能靠标题关键词硬删。

补读正文同样有成本。应区分已取得信息能完成的筛选和必须新增请求才能完成的筛选，记录净减少了多少作者请求，而不是笼统声称“先筛选就能省钱”。

## 6. 如果愿意调整一条原规则

可以讨论：候选每轮重新搜索、候选点赞每轮新读；作者历史基准改为每天刷新一次，并标明基准更新时间。新遇到的作者仍即时读取。

这会改变“每轮作者基准也独立重新获取”的既有要求，因此本次没有采用。实际节省取决于跨轮作者重合率，不能直接承诺省三分之二。

我们用已取得数据比较了5位作者的同一10条作品，在约2小时内，中位数变化分别约为0%、0.05%、3.9%、4.96%、5.26%。这只能支持开展缓存误差测试，不能证明跨天更新也足够准确。接近5倍边界的结果可能受影响。[原始观察](./采集验证/2026-09-08组合试跑/历史基准短时变化观察.json)

## 7. 建议的下一步

先把“数学上不可能达标”和“明确不相关”两类筛选的净节省量算清楚。再选择直接接口客户端做受控验证，验收真实时间、精确点赞、作者此前10条、分页停止依据和持续运行状态。

原始字段要保留，缺失和约数不能被格式化成精确数据；遇到登录或访问限制即停止，不能让API无限接管成千上万待处理作者。没有完成的范围继续显示未完成。

当前仍保持：所有菜系、图文与视频、没有推荐条数配额、历史不足不硬算。每日三轮独立刷新规则没有被本次调研更改。

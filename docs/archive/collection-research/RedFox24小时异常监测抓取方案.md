## 1. 固定产品规则

| 监测基准时刻（北京时间） | 作品发布时间窗口 |
| --- | --- |
| 今天09:00 | 昨天09:00至今天09:00 |
| 今天12:00 | 昨天12:00至今天12:00 |
| 今天20:00 | 昨天20:00至今天20:00 |

每轮窗口固定在对应时刻，不随请求执行到哪里而移动。实现时统一窗口端点口径，保存原始时间并确认供应商使用的时区。时间无法核实的笔记，不能假定属于窗口。

24小时限制的是笔记发布时间。异常比较使用本轮取得的累计点赞，不是近24小时新增点赞，也不是作者历史笔记发布后第一天的点赞。

内容范围为美食制作，不限菜系；图文和视频都纳入。正式入选作品自动保存、跨日期去重，不设置结果条数配额。

## 2. 采用哪些接口

优质库指红狐已经收录的数据集合，不等于小红书全部作品，也不自动保证实时。

| 职责 | 接口 | 请求方式与路径 | 当前文档标准价 |
| --- | --- | --- | ---: |
| 搜索新笔记 | [关键词搜作品](https://redfox.hk/apis/xiaohongshu/384C6W6B) | POST `/story/api/xhsUser/searchArticle` | ¥0.04/请求 |
| 补充笔记信息 | [作品详情](https://redfox.hk/apis/xiaohongshu/KR1LPTBF) | POST `/story/api/xhsUser/queryWorkDetail` | ¥0.04/请求 |
| 取得作者参照 | [作者作品列表](https://redfox.hk/apis/xiaohongshu/XN3ULENA) | POST `/story/api/xhsUser/queryWorkList` | ¥0.04/请求 |

15项接口已有调用记录后，建议下一轮候选发现采用普通搜索加爆款笔记洞察：洞察实测提供2篇旧样本未见的窗口内候选。黑马、日榜和七日榜本次未取得有效样本，不放进必经流程；转文案本次解析失败，评论需24小时后取结果，暂不作为当前轮次的必要补充。详见[全接口实测报告](./采集验证/2026-09-09红狐全接口实测/全接口实测报告.md)与[接口应用清单](./RedFox小红书接口应用清单.md)。新增入口仍执行相同的24小时筛选和5篇作者历史核验。

搜索结果已经列有正文、发布时间、作者编号、作品类型和互动值。因此不默认逐篇再买一次详情，也不额外查询作者粉丝数或账号总点赞来计算异常。

字段和价格依据：[搜索元数据](https://redfox.hk/story/web/api/doc/detail/no/384C6W6B)、[详情元数据](https://redfox.hk/story/web/api/doc/detail/no/KR1LPTBF)、[作者列表元数据](https://redfox.hk/story/web/api/doc/detail/no/XN3ULENA)。本次文档读取成功，不等于这三条业务接口已通过真实采集验收。

## 3. 单轮处理流程

### 第一步：新建本轮任务，锁定时间窗口

记录轮次、窗口起止、实际开始与完成时间。09点、12点、20点各自重新搜索和取数。

共享的历史信息仅用于已推荐去重与往期展示。上一轮未推荐候选、旧点赞和旧作者基准，不直接成为下一轮的计算输入。

采集需要耗时，提前量要通过实测确定。可以提前预取，但窗口末段必须补扫，才能表示覆盖到了监测时刻；没有整点历史快照时，也不能把稍后取到的点赞写成整点精确值。

某轮未完成时保留上轮结果并标明更新中。保存监测时点与真实完成时点，避免把提前截止或尚未完成的采集写成完整新轮次。

### 第二步：按关键词搜索近期候选

先沿用8个试跑词：美食教程、家常菜、面食、烘焙、甜品、自制饮品、美食复刻、创意料理。它们是待验的覆盖清单，不代表搜遍所有菜系和制作内容。

主路径使用最新排序。第一次请求示意：

```json
{"keyword":"美食教程","offset":0,"sortType":"_2","exactMatch":false}
```

`offset` 是已经跳过多少条，按文档依次用0、20、40等值翻页。实际每页数量及终止标志要用真实返回验证，不能把文档步长当成每次必定得到20篇。

该接口没有时间筛选入参。因此由工作台读取真实发布时间，保留本轮24小时内的笔记。

翻页按以下规则处理：

- 处理完当前页，再判断有没有下一页，避免丢掉有数据的末页。
- 核实结果确实按发布时间倒序后，读到完整一页都早于窗口起点，才可据此结束该关键词。不能看到一篇旧帖就停止。
- 如果出现时间缺失、排序异常、反复返回同一页或供应商截断，记录覆盖不完整，不能报告搜完。
- 最热排序只作补充取样。它不能按旧帖时间直接停止；如果最新排序已覆盖同一库中该词的全部窗口结果，就无需为重复覆盖再付费。

搜索接口没有图文/视频筛选入参。可以按返回类型保留两类，但必须统计实际覆盖；某次结果只有视频，不能据此宣布图文也已覆盖。

### 第三步：提前去重和筛选

先把不同关键词下的同一笔记合并，再排除已经推荐过的作品。用平台作品编号去重，不用标题或作者昵称。

然后筛选真实时间与制作内容。依据是否有做法、配方或制作过程，不只看“美食”标签，也不把所有探店、吃播或厨具推广当成制作内容。复刻餐厅菜、便利店自制等仍可符合条件。

所需字段齐全且数据满足本轮刷新要求时，直接使用本轮搜索结果。缺时间、类型、正文或点赞依据时，再按作品编号调用详情。

详情仍无法补齐的候选，记录具体缺口。不能把缺失点赞填成0，也不能仅凭短标题编造配方、步骤或视频内容。若制作证据仅在媒体里，需额外读取媒体才能确认；这部分请求及成本另行记录。

### 第四步：按作者读取历史，确定真正的此前5条

只对仍有资格参与异常判断的候选查询作者历史。直接使用候选返回的作者编号，无需先通过昵称搜索作者。

请求示意：

```json
{"userid":"候选中的作者编号","offset":0,"sortType":"_2"}
```

先按时间倒序取一页。若不够，再按20的偏移继续翻页；处理最后一页后再判断结束。

对每篇候选P，单独确定其参照集合：

1. 排除P本身及发布时间晚于P的作品。
2. 排除有明确布尔标记的置顶视频，再按真实发布时间排序。图文仍参与参照；置顶状态未知的视频不能当作未置顶。
3. 在剩余作品中确定紧邻P之前的5篇，不按是否热门、是否与本次关键词相关来选择历史。
4. 对这5篇核对点赞和时间。某篇缺数据时补它的数据，不能用更早的第6篇替代，凑出“有效5篇”。

作者日期范围参数可在验证后用于减少分页，但目前说明写日期、示例带时分秒，不能直接假定能精确卡到候选发布时间。最终严格比较仍由工作台完成。

同一作者在本轮出现多篇候选时，**本轮取得的历史列表可以共用**；仍须分别选出每篇候选之前的5篇，不能给它们套用完全相同的5篇。下一轮重新获取该作者数据。

优质库可能只收录部分作品，这是待验风险。即使接口返回20篇，也不能据此确认其中包含平台真实此前5篇；必须用可靠主页样本对照作品编号和顺序。

### 第五步：计算异常倍数

```text
异常倍数 = 候选本轮累计点赞 ÷ 作者此前5篇本轮累计点赞的中位数
```

5个点赞数排序后，第3个值就是中位数。例如中位数100赞，候选当前1200赞，异常倍数为12。

以5倍作为初始试跑线，正式阈值仍通过样本确定。不添加未经确认的500赞、1000赞等绝对入选门槛。

历史不足5篇、中位数为0、历史缺失或互动精度不够时，分别记录参照不足、取数缺失或精度不足。不能算成无穷倍，也不能将失败包装成未达标。

只有时间、内容和作者参照都合格，且达到当前异常阈值，才进入正式推荐结果。字段为整数不等于已证明精确，数据源验收仍是前提。

### 第六步：保存整轮结果并更新页面

所有合格作品保存到往期库，同时形成已推荐记录。保留标题、封面、作者、原文链接、类型、发布时间、本轮点赞、此前5篇依据、中位数、异常倍数、轮次及实际取数时间。

记录必须能解释“这篇为什么入选”。重跑同一轮或重复取到同一作品，不应重复生成推荐。

首页读取已经生成的结果；用户刷新页面不触发收费采集。结果准备好后更新，仍在执行时显示更新中。

正常完成但零入选、部分覆盖、数据源失败需要分开表示。候选取数失败不计作0个爆款；未推荐的作品如果仍在下一轮窗口中，可以在重新搜索发现后继续参与判断。

## 4. 怎样省钱而不改变原规则

主要采用四项措施：先做时间与内容筛选；先排除已推荐笔记；同轮同作者只获取所需的一份历史；本轮已有完整合格信息时不重复补详情。

进一步可做严格数学排除：若候选点赞是本轮准确非负整数，在中位数为0不入选的既定规则下，5个整数的正中位数最低为1。五倍门槛至少要求5赞，因此0—4赞的候选不可能进入当前五倍结果。

这只是一项有条件的实现优化。不能用过期或估算的0—4赞跳过作者；也不能借此认定作者参照一定正常。阈值修改时须重新检查该条件。正式对照验证前，不将它计为已实现节省。

不跨轮复用旧点赞或旧作者基准，不只核验点赞前20名，也不随意设置最低点赞数。这些做法会改变原规则。

## 5. 原方案的真实成本结构

仅使用上面三个标准价接口时：

```text
单轮费用 = 0.04元 ×（搜索请求数 + 作者历史请求数 + 详情请求数 + 额外重试请求数）
```

作者历史按请求页数计费，不等于永远一位作者一次。详情也可能包含候选详情和必要的历史作品补查。

例如一轮实际用了40次搜索，筛后有80位作者且每位一页足够，再补20次详情：

| 项目 | 请求数 | 费用 |
| --- | ---: | ---: |
| 搜索 | 40 | ¥1.60 |
| 作者历史 | 80 | ¥3.20 |
| 补详情 | 20 | ¥0.80 |
| 单轮合计 | 140 | **¥5.60** |
| 若每天三轮规模相同 | 420 | **¥16.80/日** |

30天按同样规模是¥504。这是说明费用构成的算例，不是候选量预测，也不限制最终结果数量；未计AI、服务器、媒体读取、额外分页和异常重试。

若一轮最终需要查1000位作者，每位仅一页，作者部分就要¥40。当前规则下，作者数和分页数是成本大头，不能沿用之前每日一版榜单方案的¥0.84/天估算。

精确预算必须由试跑取得：原始命中量、去重后数量、符合24小时数量、制作类数量、有效作者数、每作者页数、补详情率和实际扣费。

## 6. 三个必须验清的能力

**新笔记收录：**最近几个小时发布的普通制作笔记能否被搜索到。供应商已收录多少、漏了什么，需要同可靠样本对照；不以网页标题“优质库”推断覆盖。

**本轮数据新鲜度：**09点、12点、20点重新请求时，能否取得对应的新数据。保存供应商同步时间和本次获取时间；没有同步依据时标为未知。同一数值没有变化，也不能单独证明缓存未更新，因为作品可能确实没有新增互动。

**作者历史完整和精确：**包含真实普通作品，能按时间取到此前5篇，且点赞不是约数或估算。样本能对齐不等于全库获得完整保证，运行时仍记录不足与异常。

上述任一关键能力不满足，就不能把纯RedFox优质库方案宣布为已经可用。

## 7. 红狐实时接口的位置

2026-09-09复核，独立文档中的实时搜索、作者列表、基础详情仍标记为测试中。

- [实时搜索](https://doc.redfox.hk/474468723e0.md)支持一天内、图文/视频、排序和页码，更贴近本项目。但未明确每页数量、最大页数与结束标志。
- [实时作者列表](https://doc.redfox.hk/474467074e0)有发布时间、编辑时间、同步时间、置顶和下一页信息；请求却未完整说明翻页参数。
- [实时详情](https://doc.redfox.hk/474468212e0.md)有互动是否估算的标记，示例为估算。整数点赞不能因此直接用作精确基准。

这些是待测的替换通道，具体可用性、费用和数据口径未核实。不能看见“实时”二字就默认它解决了新鲜度、完整性和精度。

若优质库只适合发现候选，就只保留它的发现职责；对存在缺口的详情或作者环节单独更换经验证的通道，再重新计算成本。产品的24小时、三轮与作者异常规则保持不变。

## 8. 当前验证顺序

先验证三个主接口，不启动正式自动监测。小样本仍采用2元总预算、最多32次请求的上限，按三个接口当前标准价最多¥1.28；真实费用以账户扣费为准。未知价格的实时接口不自动纳入该预算。

验证依次围绕：搜索新笔记与类型覆盖；详情能否补齐及其刷新依据；作者此前5篇的编号、顺序、点赞和分页。通过后再按真实09/12/20三个轮次观察更新与覆盖情况。

调用预算限制的是试验规模，不限制正式合格结果数。触及预算或接口上限时，应报告局部验证，不能报完整一轮已完成。

当前已在本地配置RedFox密钥并完成22次请求的小样本，按标价及未收录免扣说明预计0.80元，保守按全部请求计费为0.88元，尚未核对账户账单。搜索、详情和作者分页已实际调用；数据新鲜度、历史完整性和连续稳定性仍未通过正式验收。具体结果见[首轮试跑记录](./采集验证/2026-09-09红狐试跑/试跑记录.md)。

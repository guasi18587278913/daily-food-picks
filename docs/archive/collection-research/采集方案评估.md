# 美食博主工作台：采集方案评估

日期：2026-09-08。

后续讨论更新：用户因费用考虑暂停纯API正式试跑，要求评估组合方案。当前建议调整为“浏览器承担批量发现和作者历史，TikHub补缺并做少量交叉搜索”，详见[组合采集方案（讨论稿）](./组合采集方案.md)。以下保留此前工具评估与6次实测依据；组合方案尚未正式试跑。

结论：建议把 TikHub App V2 作为首版主采集方案的优先候选，保留浏览器路径用于核对和备用。其搜索、翻页、详情、作者历史已完成小样本验证。是否比浏览器覆盖更全、长期是否稳定，仍需同时间窗口对照，不能由本次样本推断。

原先选定的 xiaohongshu-mcp 是初始方案。用户随后要求对比其他开源工具和 API，本文件记录重新评估依据，尚未替用户确认最终换源，也没有部署网站或定时任务。

读取了[用户提供的 X 帖子](https://x.com/servasyy_ai/status/2031594244339876192)。帖子发表于2026-03-11，本次读取正文、20条可见评论，并展开3个相关子讨论，合计得到25条不同编号的可见回复。

这不代表全部回复。页面显示的回复总数、折叠回复与实际可读数可能不同。没有把未读取的内容描述为已读。

正文提到 MediaCrawler、Agent-Reach、jina-cli、x-tweet-fetcher。评论还提出 Crawl4AI、RPA、通过 Grok 搜索 X，以及使用接口取数的建议。

几条有用的评论线索：

- 有人建议 Crawl4AI，但未提供针对小红书这套流程的实测。[原回复](https://x.com/ien0ne/status/2031806653570695625)
- 有人建议改用 RPA；没有指定产品和配置，无法比较稳定性或成本。[原回复](https://x.com/FUCK_CCTV/status/2032172227563831521)
- Grok 搜索那条讨论没有最终补出具体项目地址，不能把它当成一个已核实的替代工具。[原讨论](https://x.com/zhishiai6/status/2031615517417672738)

以上评论用于发现待验证问题。技术能力结论以当前官方文档、源码和本次取数为依据，不按点赞数或项目星标数决定。

## 2. “全面”需要拆开衡量

MCP 是一种工具接入规范。它本身不决定数据量；决定数据量的是背后的程序、取数入口和停止条件。

本次网页实测：一个关键词按“最多点赞＋一天内”先返回22个项目，其中20篇笔记、2条推荐搜索词。继续滚动后变为40篇不同笔记，仍有更多结果。因此，20篇不是这个网页数据源的上限。

原版 xiaohongshu-mcp 目前只读取已加载的搜索数据，没有继续翻页或滚动的搜索循环。用户担心它少取数据，有具体依据。[搜索源码](https://github.com/xpzouying/xiaohongshu-mcp/blob/332d196854a9eac0d2b8c2c0e3d0cc43139d724c/xiaohongshu/search.go)

评估时应分别看：

1. 关键词和内容方向是否覆盖目标领域。
2. 是否继续读取后续页面，以及因为什么停止。
3. 是否保留真实发布时间、作品编号、作者编号、互动数据及置顶标记。
4. 是否在目标时间完成更新，以及失败时能否如实提示。

即使翻到某次搜索的末页，也不能证明抓到了小红书全站的全部美食制作内容。API 也不能自动提供这种保证。

## 3. 方案对照

| 方案 | 已核实能力 | 对当前工作台的判断 |
| --- | --- | --- |
| TikHub App V2 | 搜索支持时间、排序、类型和分页；本次取得详情、作者历史、真实时间与置顶 | 主采集方案的优先候选。需要付费，仍需验证不同时间段和更深分页 |
| 原版 xiaohongshu-mcp | 登录、普通搜索、详情和作者列表可用；本机带条件搜索存在等待问题 | 不宜直接把未经修正的版本当作完整采集底座；可保留为已知方案和核对路径 |
| OpenCLI | 搜索支持一天内、最新、最多点赞、视频与图文；已实现滚动采集 | 免费浏览器路线中值得测试，但还要补真实发布时间和历史字段 |
| Agent-Reach | 当前负责选型、安装、体检与路由；小红书优先调用 OpenCLI，MCP 为备选 | 它本身不是新增的数据源，不必再作为业务采集的中间层 |
| MediaCrawler | 有搜索页码和作者游标分页、详情采集 | 当前许可限制商业用途；给业务工作台选型时不直接采用，除非解决授权问题 |
| Crawl4AI / RPA | 通用网页抓取或界面自动操作能力 | 可以自建适配，但仍要自己处理登录、筛选、翻页与字段；不会天然扩大数据源覆盖 |
| jina-cli / x-tweet-fetcher | 前者做 URL 阅读、通用网络搜索和批量 URL 处理；后者面向 X 内容读取 | 可做其他资料阅读，不能直接承担这套小红书候选与作者历史流程 |

### 开源项目的几个具体边界

**OpenCLI：** 当前搜索数量参数默认20、范围1–100，滚动受时间、轮数和无新增条件约束。100是参数上限，不是保证能获得的数量，也不是全平台上限。作者命令还有独立的滚动限制。[搜索实现](https://github.com/jackwener/opencli/blob/8271afc67e8504bda94c147f446ee29775d08274/clis/xiaohongshu/search.js)、[作者实现](https://github.com/jackwener/opencli/blob/8271afc67e8504bda94c147f446ee29775d08274/clis/xiaohongshu/user.js)

OpenCLI 搜索输出的日期由笔记编号估算，并非官方发布时间字段。这个差别在本次样本中确实存在：一篇锅包虾视频的编号对应9月2日，真实发布于9月7日。直接按编号日期过滤，会误删仍在24小时窗口内的作品。[日期估算代码](https://github.com/jackwener/opencli/blob/8271afc67e8504bda94c147f446ee29775d08274/clis/xiaohongshu/search.js#L168-L184)

**Agent-Reach：** 3月帖子的介绍不能直接代表9月版本。当前首选已是 OpenCLI；走 MCP 备选时仍依赖原项目。[当前路由说明](https://github.com/Panniantong/Agent-Reach/blob/da5044d26fc6adddb6554d5679c94ac22e76e428/README.md)

**MediaCrawler：** 当前“非商业学习使用许可证1.1”要求商业用途取得版权所有者书面同意。它还有输出作者匿名标识等适配点，不能只看“支持小红书”就直接用于按作者回查的业务流程。[许可证](https://github.com/NanmiCoder/MediaCrawler/blob/d6f7c5bb906b6dac40ddf343ef9e26438a3de092/LICENSE)、[保存字段](https://github.com/NanmiCoder/MediaCrawler/blob/d6f7c5bb906b6dac40ddf343ef9e26438a3de092/store/xhs/__init__.py)

**Crawl4AI：** 支持浏览器会话、执行页面动作和滚动采集，但它是通用基础工具。[官方能力](https://github.com/unclecode/crawl4ai)

**jina-cli：** 当前版本已经有网络搜索和批量 URL 读取，原帖将其概括为只能单页不够准确；不过这仍不是小红书专用的时间筛选与作者历史接口。[当前文档](https://github.com/geekjourneyx/jina-cli)

**x-tweet-fetcher：** 其主定位是 X/Twitter 内容读取，适合读这类讨论，不作为本工作台的小红书主采集工具。[项目说明](https://github.com/ythx-101/x-tweet-fetcher)

## 4. TikHub 的实际验证

用户提供的密钥已保存为项目本地配置，权限仅当前用户可读写，并加入版本管理忽略规则。再次与用户确认过的剪贴板核对一致。报告不包含密钥。

本次预算上限6次调用，实际调用6次。全部返回HTTP成功且业务状态成功；按公开单价估算约0.06美元，未超过预设额度。

| 调用 | 验证内容 | 结果 |
| --- | --- | --- |
| 1 | 美食教程、一天内、最多点赞、类型不限，第1页 | 20篇视频 |
| 2 | 同一搜索会话第2页 | 20篇视频，与第1页无重复 |
| 3 | 已通过网页核对的面食笔记详情 | 获得点赞与真实发布时间，发布时间和网页一致 |
| 4 | 同一作者作品列表 | 22篇，含2条置顶；按时间取得的此前10篇与网页样本完全一致 |
| 5 | 相同关键词、一天内、最多点赞，明确选择普通笔记 | 20篇图文 |
| 6 | 编号日期与发布时间明显不同的视频详情 | 返回真实发布时间，与网页一致，没有错用编号日期 |

面食样本的10条历史作品，编号和发布时间均逐条匹配。API这次读取时该笔记3463赞，前10条中位数124赞，约27.9倍。它是用于验证字段和算法的已知样本，不据此直接加入当前推荐轮次。

“类型不限”的前两页恰好全是视频，不能证明接口永远不返回图文。但首版若要同时覆盖两类内容，建议显式分别搜索视频和图文，再按笔记编号合并，避免依赖混合排序自然兼顾两类。

作者返回的时间单位为秒，网页样本为毫秒，转换后匹配。不能把接口最外层的响应生成时间当成笔记发布时间，也不能把更新时间或编号生成日期混用。

本次作者列表一页已足够取得10条，没有再调用作者第二页。搜索只实测两页，尚未确定可翻页的最高上限。

## 5. TikHub 的费用与资料边界

小红书 App V2 的公开单价为0.01美元/请求。一次请求不等于一篇爆款：搜索页、作者作品页、详情分别消耗调用。[官方报价](https://tikhub.io/xiaohongshu-api)

单轮成本应按实际请求次数计算，而不是预设爆款条数。页面返回的免费缓存链接，只能重读那一次响应；不能把09:00的缓存作为12:00的新数据。[计费与缓存说明](https://tikhub.io/pricing)

HTTP错误通常不收费，但有些业务错误可能包在成功响应中，仍然计费。因此正式采集需要同时检查HTTP状态和业务数据是否有效。[作者接口提示](https://docs.tikhub.io/420136396e0)

Web V3 的维护状态在官方资料中存在矛盾；本轮验证使用 App V2，没有依赖这项尚未澄清的路径。[迁移说明](https://blog.tikhub.io/zh/article/7)、[当前产品页](https://tikhub.io/xiaohongshu-api)

官方排错说明还提示，小红书接口遇到400时，有些情况可能需要等待30–60分钟。本次6次调用未遇到这种情况，但它意味着准点更新和长期稳定性仍需实测，不能用一次成功替代连续运行观察。

TikHub 是第三方数据服务。评论中的“官方API更稳定”不能直接视为对TikHub的稳定性保证。

## 6. 这次能下什么结论

可以确认：我们的相对爆款规则能用真实数据计算；网页有超过首屏的内容；TikHub 的必要接口已取得有效样本，且能提供原版MCP输出中缺失的字段。

暂不能确认：TikHub比网页覆盖更全、所有作者一页都足够10条、分页能无限继续、或每天三个轮次的长期稳定性。

前面的网页搜索和后面的API搜索发生在不同时间，不能直接用各自返回数量或重合率判断覆盖优劣。某篇笔记刚好越过24小时边界，也会导致两个结果集不同。

## 7. 后续同条件对照怎么做

1. 使用同一批关键词，尽量在相同时间采集，统一按明确的北京时间窗口核对真实发布时间。
2. 两边都分别查询图文和视频，记录每页新增、重复、停止原因和实际覆盖边界。
3. 对候选临时读取作者历史，按真实时间选取此前10条；不足时继续分页或标明未取足，不能假定前10项就是此前10篇。
4. 记录时间有效、内容相关、历史完整、数据达标和跨轮新增各环节的数量。
5. 比较各方案独有的合格作品、重合情况、成功率、耗时及实际成本。没有全平台真值时，只能做相对覆盖比较。
6. 合格结果有多少就保存展示多少。采集预算或平台上限造成的截断必须单独记录，不能说成“没有更多爆款”。

正式运行仍保持09:00、12:00、20:00三轮独立，只共享已推荐作品去重记录。每轮用新取得的数据判断，往期保存入选时的数据和原文链接。

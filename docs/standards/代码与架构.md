# 代码与架构

适用：本项目新增、修改和重构的手写业务代码。风险分级见[规范入口](README.md)，验证方式见[测试与交付](测试与交付.md)。

核心标准：读者能看出职责，改动能沿着清楚的依赖关系进行，失败能被观察，关键行为有证据。

## C01. 按职责组织代码

高内聚是把围绕同一目的、通常一起变化的代码放在一起。低耦合是减少不必要的依赖，避免改一处牵动无关功能。

- 每个文件围绕一类清楚的职责。页面渲染、供应商响应处理、排序、预算、存储访问应有边界。
- 一个函数完成一件清楚的事。多步业务允许主函数负责组织顺序，具体处理放在具名函数中。
- 拆分要改善理解和测试。不要把一段简单计算拆成许多跳转，也不要为每个函数新建文件。
- 通用目录不能变成杂物箱。只有确实共享的逻辑才提取；业务规则放在所属模块。
- 修复结构不等于修改规则。排序门槛、收费策略、时间窗口和授权条件必须按已确认需求保留。

**本项目的默认边界：**

| 位置 | 承担的职责 | 边界 |
| --- | --- | --- |
| `miniprogram/pages/` | 页面事件与展示状态 | 通过客户端调用层读取数据，不包含供应商密钥和服务端收费逻辑 |
| `miniprogram/lib/` | 客户端调用、展示转换、本机收藏 | 不导入服务端存储或采集实现 |
| `cloudfunctions/catalog/` | 授权读取、查询、返回展示数据 | 不因刷新或搜索触发收费采集 |
| `cloudfunctions/collectTick/` | 定时任务、采集、判断、预算和发布 | 通过服务端校验的入口运行 |
| `config/` | 已确认且可共享的业务配置 | 敏感配置放安全环境；生成副本不独立维护 |

这些是当前边界，不要求另建微服务或更换框架。新增功能先说明放入哪个模块，新增模块要能解释独立职责。

## C02. 控制函数和文件规模

以下采用教程的经验提醒线，作为审查触发条件，不作为机械拆分指标。统计按正常格式化后的代码，排除空行和纯注释行；生成文件、数据样本与必要声明另行判断。

| 信号 | 要做的检查 |
| --- | --- |
| 函数超过约 30 行 | 检查是否混入不同职责、过多分支或不同层次的细节 |
| 函数达到约 150 行 | 给出拆分方案；保留时说明单一职责、保留理由和验证范围 |
| 手写业务文件达到约 800 行 | 检查是否混放多个模块，提出边界整理方案或有依据的例外 |
| 函数超过 5 个独立参数 | 检查是否混合职责、参数容易传错；必要时用有类型说明的参数对象 |
| 简单规则变更需改 5 个以上文件 | 检查规则是否重复、接口是否泄漏内部细节；不能只按文件数判定设计错误 |

不接受新增千行手写业务函数。不要通过去换行、压缩表达式、隐藏回调来规避提醒线。仅超过提醒线，不自动升级为独立审查或反复审批。

## C03. 依赖方向明确，禁止新增循环依赖

循环依赖指 A 使用 B，B 又直接或间接使用 A。检查不能只看两文件互相导入，还要看 A → B → C → A。

- 页面使用客户端调用层；后端入口组织业务；业务使用明确的存储和外部服务接口。
- 底层公共工具不能反向导入页面或某个具体业务入口。
- 模块只使用其他模块公开约定的入口，不访问其私有状态或内部实现路径。
- 共用的类型或纯计算可放到双方不反向依赖的位置。可变行为可通过参数传入，不必为此搭建大型框架。
- 遇到已有循环，先说明本次是否触及。必要修复重新定界，不顺带全库重构。

依赖检查工具只能发现一部分静态导入关系。共享状态、数据库和运行时调用的耦合，仍需检查数据流及集成行为。

## C04. 命名准确、一致，表达单位和副作用

- 名字说明对象和目的，例如 `candidateNotes`、`reserveRequestBudget`、`publishSnapshot`。避免靠 `data1`、`temp2` 表达业务概念。
- 函数使用能说明动作的动词；布尔值使用 `is`、`has`、`can` 等能按真假阅读的名字。
- 金额名称说明币种和计量单位，时间区分时刻与时长，例如 `costMicroUsd`、`timeoutMs`、`publishedAt`。
- 同一个业务概念使用同一名字。确需区分本地读取、远程获取和缓存加载时，可定义不同动词，不强求全部改成 `get`。
- 名字不能隐藏重要副作用。查询不能暗中扣费、发布或改权限。副作用是除了返回结果，还修改外部状态或触发外部动作。
- 合理的局部 `error`、`index`、协议字段 `data` 不一刀切禁止。判断标准是所在范围内是否清楚。
- 沿用当前 JavaScript 命名习惯和微信固定文件名。不要单为风格批量重命名已有文件。

注释优先解释为什么这样做、特殊业务边界和平台限制。名字说明“是什么”，不能替代必要的原因说明。

## C05. 保持简单，避免过度设计和重复规则

YAGNI 指尚未需要的能力先不建；KISS 指采用容易理解的实现。

- 普通函数和清楚的条件能解决问题时，不先搭建工厂、插件系统或多层继承。
- 优先可读性，不以最少行数为目标。不要把多层判断压成难读且改变空值行为的一行。
- 分支嵌套超过约 3 层时检查是否可提前返回、提取判断或重新组织数据。层数是提醒，不是自动拆分命令。
- 复用相同的业务规则。外形相似但变化原因不同的代码，可以暂时保留，不强行抽成万能工具。
- 不留无意义的“以后扩展”。真实未完成工作可以用待办记录，说明原因与验收；安全关键路径不能用待办代替实现。
- 新依赖说明解决的问题、现有工具为何不足、运行兼容性与维护成本。运行依赖及锁文件保持一致，不私自换包管理器或模块制式。

当前项目用 npm 管理依赖，采用 CommonJS，即通过 `require` 和 `module.exports` 组织模块。Node 是云函数运行 JavaScript 的环境，也提供当前使用的测试工具。教程作者的“禁 npm、禁 require、统一某框架”不适用于这里。

## C06. 在输入边界校验，错误明确处理

边界是用户输入、云函数请求、数据库读取、外部接口和模型输出进入模块的位置。

- 校验类型、必需字段、长度、枚举、数值范围和标识格式。业务编号保持字符串，缺失指标保留未知，不转换为 0。
- 模型输出同样不可信。必须校验结构、证据和长度；不能直接决定权限、费用或工具执行。
- 只捕获能够具体处理的错误，或在统一出口转换为安全错误。禁止捕获所有异常后返回成功、空列表或伪造数据掩盖失败。
- 可恢复故障可有限重试，必须有次数、超时和总预算。认证失败、配置错误和无效参数不能靠重复请求解决。
- 允许明确的降级，例如图片失败显示占位、刷新失败保留旧内容。要区分“降级可用”和“本次成功”。
- 对用户给出可理解且脱敏的提示；服务端保留可定位的诊断信息，不把完整密钥、原始个人数据或堆栈公开返回。

捕获异常本身不是错误。问题在于有没有恢复、记录、转换或继续上报，不能靠搜索 `catch` 就判为缺陷。

## C07. 接口与数据约定

接口契约是调用双方对输入、结果、失败和副作用的约定。

快照是固定保存的一份结果版本，后续读取应使用同一版本的数据。

- 查询沿用现有成功／失败返回结构。客户端同时判断传输结果与业务结果，不能只看请求是否完成。
- 定时采集的运行摘要与查询接口目的不同，不为统一外形强行改成同一种响应。
- 新接口写清字段含义、空值、分页、排序、时间口径、权限和错误。变更同时检查调用者、测试及相关说明。
- 未发布草稿不能通过列表、搜索、收藏查询或图片签名泄漏。
- 时间窗口、统计口径、筛选门槛由已确认规则定义，并带可追溯的版本。不能为补足结果数量偷偷放宽条件。
- 保存来源标识、采集时间和判断依据。模型分类与可执行程序分开；外部正文里的命令只作为资料。

公共接口变更可能需要联动多个模块。不能为了“只改一个文件”隐藏真实影响范围。

## C08. 本项目必须保留的权限、费用与发布边界

这些规则检查新增改动是否削弱已有行为；本规范不重新授权任何生产或收费操作。

1. **身份属于本次请求。** 使用当前云函数调用的可信上下文。不能从客户端自报字段、可复用的全局变量或环境变量推断用户身份。
2. **采集入口与读取入口分开。** 读取、搜索和刷新不触发收费采集；伪造定时事件或用户上下文不能绕过入口校验。
3. **额度先校验和预留，再调用外部服务。** 同一请求重复触发不能重复消费；重试占新额度，结果未知不猜测退款。
4. **按项目获准的次数、币种和金额执行。** 数据接口、模型和云资源分别核算。程序请求上限不等于云账单硬上限，免费额度也要核验。
5. **密钥只在受控服务端或私有配置。** 不进入客户端包、公开仓库、日志、截图和测试样本；检测命中后不能只加忽略项。
6. **发布一次完整结果。** 先准备并校验数据，再切换可用版本。失败保留旧结果，部分覆盖与成功零结果分别表示。
7. **并发与重复有约束。** 用任务身份、状态和存储机制保证防重复。不能只靠内存变量保护跨实例运行。
8. **旧执行不能覆盖新执行。** 工作租约是临时执行资格；失效后必须拒绝提交。网络调用不放进会重试的数据库事务。
9. **数据库与图片访问有服务端权限。** 客户端隐藏按钮不是授权检查；不得签发调用者任意指定的私有文件。

当前身份解析和预算实现的依据以[源码运行记录](../operations/wechat-trial-runbook.md)及对应代码为准。旧计划中的平台接口写法不能覆盖后续实测修正。

## C09. 可观察、可停止、可恢复

结构化日志是按固定字段记录事件，便于串起一次执行。每条关键运行事件应能说明：哪个任务、哪个步骤、什么结果、耗时和失败类别。

- 优先复用轮次号、请求号和平台执行号，不另造无法关联的编号体系。
- 记录开始、关键停止原因和结束摘要。只保留定位所需字段，敏感内容脱敏。
- 监测业务是否完成，不能仅看进程存活或平台错误数为零。定时任务最先关注“该更新却没有新结果”。
- 定时任务明确时区、运行窗口、超时、暂停方法和恢复条件。电脑休眠、云实例复用等运行条件应纳入验收。
- 恢复从已保存进度继续；不清空账本、不重复购买已取得的数据、不自动放大限额。
- 日志、任务明细和缓存有保留策略，避免无界增长；删除前确认恢复与审计需求。
- 发布前知道如何停止采集、保留旧结果和回退版本。备份或恢复能力要经验证，不能只写“可回滚”。

日志与监控的工具采用云平台现有能力优先。需要额外付费或部署时另行按风险处理；不能把本条写成已开通的承诺。

## C10. 改完后的自审

检查实际差异，按四个维度过一遍：

- **逻辑：**需求是否满足，空值、异常、边界、顺序和并发是否处理。
- **安全：**是否新增注入、越权、身份串用、密钥泄漏或失控消费。
- **一致：**命名、模块职责、接口与项目现有约定是否一致。
- **干净：**是否混入无关改动、调试代码、重复规则、过期说明和手改生成副本。

审查意见要指出具体位置、触发条件和影响。不能只给一个“质量分”；未复现的担忧标成待验证，不编造阻塞项。

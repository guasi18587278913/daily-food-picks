# 测试与交付

适用：开发、修复、重构、提交、合并和发布。任务风险按[规范入口](README.md)判断，代码要求见[代码与架构](代码与架构.md)。

测试的目的，是证明约定行为在已覆盖场景下成立。它不能证明所有情况都正确，也不能替代真实用户验收。

## T01. 先定义可观察的完成标准

开始写关键逻辑前，用“给定条件、执行动作、应当发生什么”列出验收场景。

每项说明输入、结果和重要副作用。例如“同一请求被再次领取时，复用原记录，费用计数不增加”。不要只写“功能正常”或“代码符合最佳实践”。

完成标准来自已确认需求。代码现状是调查材料，不能自动成为正确答案。

## T02. 三种测试各管什么

| 类型 | 验证对象 | 本项目例子 | 不能证明什么 |
| --- | --- | --- | --- |
| 单元测试 | 一小块逻辑，在可控条件下验证 | 排名计算、字段转换、预算判断、收藏存储失败 | 真实云数据库、供应商和手机一定可用 |
| 集成测试 | 模块与真实依赖边界的配合 | 当前请求身份解析、数据库事务约束、客户端与查询接口契约 | 整个用户流程及生产配置全部正确 |
| 端到端验收 | 用户或定时任务的完整链路 | 真正定时取数后，指定微信成员能看到新轮次 | 长期稳定性、所有边界和产品价值 |

单元测试中的外部依赖使用测试替身，即可控制结果的假数据库、假请求或假时钟。涉及真实依赖的检查，要明确其实际环境和范围。

测试数量不机械遵守 70/20/10。快速且稳定的逻辑测试为主，重要接缝补集成测试，关键链路做少量端到端验收。

## T03. 哪些场景先写失败测试

测试驱动开发（TDD）指先写预期行为的测试，看它因缺少正确行为而失败，再实现并整理代码。

- **新关键业务逻辑：**预算、权限、时间窗口、排序、发布一致性等，优先先写测试。
- **修复明确的 Bug：**先构造能重现问题的用例，再修复；确实无法自动复现时保留可重复的人工步骤和限制。
- **重构：**先检查已有行为测试是否覆盖要保持的结果。缺口补齐后再改结构。
- **纯文案、颜色、间距等低风险展示修改：**不写只照着实现断言的测试，采用受影响页面检查和必要类型检查。
- **文档与 Skill：**检查链接、触发、步骤、输出和读者理解，不为此运行全部业务测试。

红色阶段必须因预期行为尚未满足而失败。语法错误、依赖缺失或测试没有找到文件，不是有效的行为失败证据。

## T04. 单元测试至少考虑这些输入

按函数的真实责任选择，不能每个函数机械套全表。

| 场景 | 检查重点 |
| --- | --- |
| 正常 | 返回内容和关键副作用符合要求 |
| 边界 | 阈值前后、空集合、最大长度、开始与结束时刻 |
| 异常输入 | 缺字段、类型错、负数、过大数字、非法编号 |
| 依赖失败 | 超时、拒绝访问、响应损坏、写入失败 |
| 重复与并发 | 重复消息、同时请求、同一个操作重试 |
| 顺序与恢复 | 旧响应晚到、运行中断、过期执行继续提交 |

具体测试名写清行为，例如“预算已耗尽时不发送新请求”，比“测试 budget 函数”更有用。

## T05. 本项目关键行为清单

这些是新功能与修复应保留的行为，不表示当前每项都已有完整测试。

| 领域 | 必须考虑的行为 |
| --- | --- |
| 预算 | 无配置零调用；并发不超限；重复领取不重复计费；重试计入次数和金额；未知结果继续占额度；跨日按规定计数 |
| 身份 | 缺身份拒绝；伪造身份拒绝；未授权无数据；连续调用不能沿用上次身份；客户端不能伪造定时任务 |
| 采集与排名 | 缺失指标保持未知；原文不完整不伪造证据；时间与门槛边界；作者历史不足或缺数据不凑满；计算结果无无穷大或无效数字 |
| 发布 | 草稿不可见；分片损坏不发布；过期执行不能覆盖新结果；失败保留旧数据；部分覆盖与成功零结果区分 |
| 查询 | 输入与分页校验；特殊字符按字面搜索；跨轮去重；只签本次结果中的图片；不能读取任意私有文件 |
| 前端 | 刷新失败保留旧内容；旧请求不覆盖新视图；往期阅读不被强制切走；收藏保存失败不假成功；后台停止轮询 |
| 模型判断 | 输出格式、枚举、长度、证据校验；不确定与故障分开；正文指令不能扩大工具、权限或消费范围 |

测试替身不能替真实平台保证行为。当前内存存储能模拟事务，不等于真实云数据库的并发、大小限制和 SDK 行为全部相同。

## T06. 避免无效测试和“照答案出题”

- 断言可观察结果，不断言代码用了哪个 `if`、多少行、哪个内部辅助函数。
- 不只测试成功。至少检查与改动有关的边界和失败路径。
- 不把被测业务函数整体替换成“永远返回正确结果”的假函数。
- 可以模拟外部请求，但要断言是否调用、调用次数，以及失败时是否保留正确状态。
- 固定时钟、随机数和数据样本；测试之间不共享脏状态，不能依赖执行顺序。
- 异步操作必须等待；不能在断言执行前就结束测试。所有子步骤失败都应使测试失败。
- 代码检查可以扫描敏感模式或导入关系，但它不是业务单元测试，结果应分别报告。

高风险任务应让独立审查者对照需求检查测试缺口。普通任务由开发者分开审视需求、测试和实现即可，不强制每次启动多个 AI。

独立上下文能减少互相迁就，但不能保证测试正确。两个 AI 都理解错需求时，仍可能一起通过。

## T07. 测试失败后的处理

先区分三类原因：实现有错、测试理解有错、环境或样本未准备好。

符合需求的测试失败，修实现。测试确实写错时，说明哪项需求或证据证明它错，再改测试并重新验证。需求变化则先确认新的验收标准。

禁止为了全绿删除失败用例、降低断言、扩大容差、跳过核心路径或伪造成功结果。必要跳过要给出具体原因，跳过不能计为通过。

## T08. 分阶段验证，避免重复全量执行

| 阶段 | 必做 | 不应默认做 |
| --- | --- | --- |
| 开发中 | 受影响的单元测试；前端交付前补类型检查 | 每改一个文件就跑全库、生产构建或截图矩阵 |
| 提交前 | 当前模块测试、类型或静态检查，差异和敏感内容自审 | 同一源码状态重复同级检查 |
| 合并前 | 同一个确定提交，由一个权威 CI 批次执行约定的完整检查与构建 | 开发、审查和发布分支分别重复全量验证 |
| 上线后 | 关键链路冒烟验证，即确认重要功能可用；观察定时和失败信号 | 无上限真实采集、模型调用或压力测试 |

源码未变不重复；源码变了只重跑受影响层级。配置、测试数据和依赖变化也可能使旧证据失效，不能只看代码文件是否变化。

当前未见源码仓库中的统一 CI 配置。接入之前，不能把手动模块检查写成“合并门禁已经自动通过”。正式合并的验证安排需要单独落实。

## T10. 真实服务验证必须有边界

- 单元测试默认不访问付费数据、真实模型、生产数据库和真实用户账号。
- 真实集成验证必须说明环境、允许的写入、调用次数、费用上限及停止条件，沿用当前任务已获授权。
- 不因为“在测试”就绕过白名单、调高预算或关闭身份检查。
- 用模拟器验证页面，就报告模拟器。需要指定成员手机使用的验收，必须有该成员的实际结果。
- 定时功能需要真实触发和业务结果证据。平台执行次数增加或平台错误为零，不能单独证明更新成功。

## T11. 交付证据怎么写

每次完成关键开发任务，保留足以核对的结果：

1. **变了什么：**解决的问题与用户看到的行为。
2. **验证对象：**具体提交，或工作区差异摘要；配置和测试数据版本也需明确。
3. **验证环境：**本地、模拟器、测试云端、生产或真机，不能混用。
4. **执行结果：**命令退出码、通过数、失败数、跳过数；平台操作同时检查业务返回。
5. **实际限制：**未验收的环节、剩余问题、停止或恢复方式。

测试、类型检查、包检查、平台部署和用户验收分别报告。命令退出码为 0，但平台返回失败时，结论仍是失败。

需要精简输出时保留完整日志，并确保原始退出码没有被管道后面的文本命令覆盖。不要只看到最后一行“完成”就下结论。

## T12. 反馈形成下一次检查

每个真实缺陷记录：出现条件、期望与实际、相关模块、原因、修复证据和回归用例。

需求、接口、权限和用户流程有变化时更新相关说明；纯样式小改不要求重写整套规格。功能清单应能找到页面、动作、接口、数据、规则和测试，不强制一开始给每个按钮建立编号系统。

学习实验失败但有完整记录，可以算学习成果；已承诺的产品功能未完成，仍应标为未完成。不得用复盘代替交付。

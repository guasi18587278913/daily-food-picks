# 美食选题工作台开发规范

版本：1.0｜更新日期：2026-09-13｜状态：已按用户确认接入共同开发入口与 Spec Kit。

这套规范服务于刚启动的项目：让代码容易理解、改动范围可控、关键行为可验证，避免随着功能增加反复返工。

长期原则由[constitution](../../.specify/memory/constitution.md)维护，本目录维护具体细则。两种工具沿用[共同 SDD 工作流](../workflow.md)。格式、循环依赖、CI 和告警的接入状态见[来源与取舍](来源与取舍.md)，不能把规则文字当成已执行的检查。

用户当前明确指令和已确认的任务约定优先。本文补充本项目的代码与工程规则，不另造一套重复审批流程。发现实质冲突时指出冲突，不能私自废掉原有要求。

## 3. 每个开发任务的起点

开始前说清三件事：要解决什么、本次边界、怎样算完成。把用户已经说清的内容复述为范围即可，不要求重新回答一轮。

先用文件搜索和定向读取找到实际入口、相关调用者与现有测试。涉及接口、权限、数据或费用时，要同时看对应边界。证据足够后停止扩散调查。

| 等级 | 判断条件 | 执行方式 |
| --- | --- | --- |
| 快速 | 不超过 3 个文件、1 个业务模块；用户明确要求改动；不触及高风险事项 | 定向读取、一句话计划、实施、受影响验证、自审；不用独立审查者 |
| 标准 | 普通局部修改，通常 4–5 个文件、最多 2 个模块；两个模块的改动相互独立，不改变跨模块约定，也不触及高风险事项 | 简短文件级计划；已获执行授权且无新产品决策时直接继续 |
| 高风险 | 权限、身份隔离、数据库迁移、密钥、金额或付费、部署、持续集成、生产写入、破坏性操作；或改变跨模块契约、共享状态、依赖和职责边界的联动修改；或超过 10 个文件 | 先完成调查和可审阅方案，取得对应确认；实施后独立审查，修复后复审 |

分级以高风险条件优先。“跨模块联动”指模块之间的约定或影响关系变化，不只看文件在哪个目录。例如两个独立展示模块各改提示文案可按标准任务；查询接口换字段并调整页面调用，按高风险任务。

持续集成（CI）是代码提交后由服务器自动执行检查的流程。修改 CI 本身也可能改变项目能否拦住错误，因此按高风险处理。

预计超过 5 个文件或 2 个业务模块，先拆为可验证的小任务。每项写清涉及文件、依赖和验收方式；已有整体授权不重复请求。机械且语义单一的跨文件改动，可说明统一验证方式后整体处理。

## 4. 正常开发顺序

1. 明确目标和验收，核对相关事实。
2. 选择最小可行方案，明确模块和数据边界。
3. 对关键逻辑先列正常、边界、失败场景；按[测试规则](测试与交付.md)确定是否先写失败测试。
4. 一步一步实施，只做本次所需改动。
5. 运行受影响检查，检查差异；高风险再独立审查。
6. 交付结果和证据，更新发生变化的行为说明及待办。

已有需求、计划和任务清单时沿用它们。小修不强制生成多份文档；复杂功能应保留可接续的计划。重构指改善结构且保持约定行为，改变业务规则应另行明确。

超出已声明范围时暂停新增改动，说明必要依赖。无关问题单独记下，不以“顺手优化”扩大任务。

## 5. 调试失败时怎么做

第一轮修复失败后，停止继续补丁。重新检查输入、输出、配置、时间顺序和组件边界，换一个数据方向验证假设。

形成新的修复方案。标准和高风险任务需要对新方案确认；同一问题连续三次修复失败，应讨论结构问题，不能继续叠条件分支。

## 6. 谁来维护这些规范

长期原则只在 constitution 维护，具体规则只在对应专题维护，其他文件引用。实现人员补充真实缺口；项目负责人决定产品边界和高风险例外。

规则变更要写明原因、适用范围和验证办法。普通命名建议不制造额外审批；改变权限、费用或生产保护的规则，仍按高风险处理。

一次故障优先留下“触发条件、原因、修法、回归测试”。重复发生或后果明确的问题再形成长期规则。阶段交付时清理过期规则和重复说明。

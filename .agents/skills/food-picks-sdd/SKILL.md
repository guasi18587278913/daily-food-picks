# 美食工作台 SDD 接续

从真实项目状态继续，不重新发明开发流程。Codex 使用 `$speckit-*`，Claude Code 使用 `/speckit-*`；两者读写同一组功能材料。

每个开发任务在首次修改业务代码前完成下列入口检查；同一任务复用已读且未变化的材料。未出现在技能列表但本文件可读时，直接读取并按本文执行，并说明自动发现尚未确认。

## 先确定当前工作

1. 从包含 `.specify/` 与 Git 的项目根运行。先读 [共同入口](../../../AGENTS.md)和[项目原则](../../../.specify/memory/constitution.md)。
2. 先区分新功能、已有任务和只读讨论。新功能尚无规格时直接进入 specify，不先要求旧功能指针；只读讨论不创建文件。
3. 已有任务优先用用户指定目录，否则读取 `.specify/feature.json`，并核对其规格、用户目标与相关 Git 差异是否属于同一功能。指针不吻合或缺失时，查看 specs 与未完成任务；只有一个可确定的目标时说明依据后显式选中，多个候选无法判断时只澄清目标。最近提交仅作线索，不能单凭它切换功能。
4. 确定已有功能后，用 `bash .specify/scripts/bash/check-prerequisites.sh --json --paths-only` 确认路径，再读该功能实际存在的 spec、plan、tasks 和 Git 差异。该命令只解析路径，不证明文件存在或内容齐全。没有默认指针或用户指定另一功能时，使用下面的显式目录方式。
5. 按任务类型检查所需材料。新功能以及按任务清单实施的已有功能，应有能覆盖本次工作的 spec、plan、tasks；缺哪一阶段就先接续对应 Spec Kit 步骤，补齐后再改业务代码。已有代码但材料缺失时，以源码和可核验证据补录现状、标出未知与剩余项，不能把补录写成事前方案或伪造完成事实。小改按下面的简化路径执行。
6. 按[风险分级](../../../docs/standards/README.md)判断所需方案、授权与审查，用一句话说明“本次功能、当前阶段、对应任务或小改范围、验收方式”，然后按已有授权继续；这不是新增审批环节。

任务明确指定另一功能时，给只读命令设置 `SPECIFY_FEATURE_DIRECTORY=specs/功能目录`；`--paths-only` 不改默认指针。同一工作区不要与另一任务并发切换默认功能。

## 选择路径

先判断用户是在讨论／审查，还是要求实际开发；只读意图优先，不因提到新功能就写规格或代码。

- **新功能**：调用对应 `speckit-specify`；必要时 clarify；然后 plan、tasks、analyze、implement。关键行为测试必须进入需求与任务，不留到最后临时补。
- **继续已有任务**：读取现有材料和证据，定位未完成项；材料齐全时直接接续 implement。不要重跑会覆盖已有 plan 的初始化脚本。
- **修复或小范围调整**：沿用所属功能，先调查并按风险制定最小方案。关键 Bug 先建立失败用例；纯展示小改不强制整套 SDD 文档。
- **只讨论、解释或审查**：保持对应只读范围，输出判断或问题，不执行实现、部署和收费调用。

新产品决策或任务实质扩张先对齐。不能因规范有检查清单，就让已经授权的小改重复审批。

## 按需读取细则

- 写或重构代码：[代码与架构](../../../docs/standards/代码与架构.md)。
- 写测试或声称完成：[测试与交付](../../../docs/standards/测试与交付.md)。
- 创建或修改 Skill：[Skill 编写与维护](../../../docs/standards/Skill编写与维护.md)。
- 跨工具接手、功能切换、状态维护：[SDD 工作流](../../../docs/workflow.md)。
- 云端事实及已批准额度：读取当前任务引用的运行记录，不能只按历史研究推断。

## 实施与完成

保持模块边界，只改已声明范围；不写生成副本。受影响测试、类型或结构检查按阶段执行，不反复跑同级全量验证。

检查失败先区分实现、测试和环境原因；不能改断言、清预算、隐藏失败或降低权限检查来继续。高风险独立审查发现阻塞后修复并复审。

在 tasks 原条目更新完成状态；同一任务编号只保留一个当前状态，不另复制一组同号勾选。接手时发现状态矛盾，先对照源码与运行证据核实；无法确认的项保留未验证说明，不猜测勾选。

在功能文档或它引用的运行记录中保留：当前源码、已完成任务、验证结果、未完成项和下一步。规格质量清单的勾选不是实现完成，也不是新的操作授权。交付时分别说明规则已写入、静态检查通过与真实会话触发已验证的实际状态，不能把前两项当作第三项。

没有新结果就不制造进度。产物缺失、工具未加载、路径有歧义或权限不足时指出具体问题；继续不依赖它的工作，不谎称已经完成。
